# Examples

Each example is one file. Install the wheel first, then run the file:

```bash
python examples/live_preview.py              # Weevia S1, found by name
python examples/live_preview.py --synthetic  # no camera
python examples/live_preview.py --help       # every option, and what the example writes to the camera
```

| Example | What it does | Writes to the camera | Without a camera |
|---|---|---|---|
| `quickstart.py` | Opens the camera, prints the negotiated mode, shows both eyes; `s` saves a pair | none | no |
| `live_preview.py` | Both eyes side by side in a window, with the frame rate the loop receives | none | `--synthetic` |
| `save_stereo_pairs.py` | Left/right PNG pairs on the space key or every Nth frame, plus `pairs.csv` (index, host_ns, driver_ns, driver_clock; the driver columns empty with DirectShow and `--synthetic`, filled on Windows with `--backend msmf`, run without a camera only) and `capture_info.json` (mode, control values, SDK version) | none | `--synthetic` |
| `record_video.py` | Both eyes side by side into one video file (MJPG `.avi` by default, or lossless FFV1 `.mkv` with `--lossless`), a CSV of frame times (`host_ns`, and `driver_ns`/`driver_clock` where the capture backend gives them: on Windows `--backend msmf`, not DirectShow; run without a camera only) and a `.json` of the mode and control values; the lossless file's pixel values: generated frames only; not run with the camera | none | `--synthetic` |
| `play_recording.py` | Reads that recording back through `Device` as if it were the camera, and shows or counts the frames; `--start`/`--start-seconds` seek, `--real-time`/`--speed` pace it, `--loop` repeats; reading a recording back, seeking and looping: verified with the published 0.0.7 wheel on one Weevia S1 unit, Windows 11, one PC, two-level USB hub, two USB re-insertions, read-only; the `--speed` factor: not verified | no camera | needs no camera |
| `list_controls.py` | Every control the camera advertises: current value, range, default, how far its effect is verified | none | `--synthetic` |
| `set_controls_once.py` | Manual exposure and gain in one `set_many()` call at startup; prints readback and `kept` | one `set_many()` call | `--synthetic` |
| `presets.py` | Saves every control to a JSON preset; `--load FILE` lists what differs and loads it, printing readback and `kept`; run without a camera only | none when saving; `--load`: one `set_many()` call | `--synthetic` |
| `led_level.py` | Sets the IR illuminator level once and compares the image before and after | one write | `--synthetic` |
| `measure_fps.py` | Intervals between frames from `host_ns`: mean, min, max, late frames, repeated images. Where OpenCV passes on the capture driver's time stamp (`driver_ns`: Linux V4L2; Windows only with `--backend msmf`, which finds the Weevia S1 by name in the Media Foundation list (the name lookup itself: run with the camera in two USB re-insert cycles, one PC, one camera, 2026-11-25, the published 0.0.7 wheel); none with DirectShow), the same intervals on that clock, the first frame's driver time (not the start of streaming: about 364,400 s on one PC with one camera, once — use differences) and how far each frame trails the earliest (`host_ns - driver_ns`); `--backend msmf` and DirectShow run with the camera once (one PC, one camera, 2026-11-24): MSMF 276 of 900 frames per eye repeating the previous image with driver-time intervals of 11.11 ms (mean, min and max), DirectShow 0 of 900 — see `StereoFrame` in `API.md`; on Linux (V4L2, experimental) run with the camera once (one PC, one camera, 2026-11-25, the 0.0.6 wheel); its `Device.repeated_frames` line came later: run with the camera once (one PC, one camera, 2026-11-25; the example's output does not record the OpenCV version): through `--backend msmf` 271 of 900, with the repeated-images warning once; through DirectShow 0 of 900, no warning | none | `--synthetic` |
| `capture_dataset_npz.py` | N frames into one `.npz` (`left`, `right`, `host_ns`) for training or analysis, and a `.json` of the mode and control values | none | `--synthetic` |
| `torch_dataloader.py` | Reads that `.npz` with a PyTorch `Dataset` and `DataLoader` (needs `torch`) | no camera | needs no camera |
| `list_devices.py` | Video devices Windows reports, in DirectShow's order (`--backend msmf`: Media Foundation's; the two lists can be in a different order (seen once on one PC, with `list_devices(backend="msmf")` — not with this example); Linux: the V4L2 capture nodes, `--backend v4l2`, the default there — not run with the camera on Linux), and how many are a Weevia S1; each device's USB location when Windows reports one; what to do with none or two; `--verbose` adds one line each for its `vid`, `pid`, `bcd_device` and `link_speed` (`DeviceInfo`, read without opening the device). `--backend msmf` and the doctor's Media Foundation list: run with the camera in two USB re-insert cycles (one Weevia S1 unit, one PC, 2026-11-25, the published 0.0.7 wheel), listing the Weevia S1 by name; `--verbose` (the USB IDs and the link speed): run with the camera in the same two cycles (Windows 11, two-level USB hub; not opened); the USB locations: the DirectShow list has been run with the camera once (one PC, one camera, 2026-11-25, with the 0.0.6 code) | no camera | `--synthetic` (a made-up list) |
| `open_by_usb_location.py` | Each Weevia S1 and its USB location; `--usb-location` opens the one at that location (`DeviceConfig.weevia_s1(usb_location=...)`) and reads one frame — how to open one of two cameras that share a name. A USB location is not a serial number: it names the port the camera is plugged into, and it changes when the camera is plugged into another port. Using two cameras at the same time is not supported. Picking a camera by USB location has been run with the camera once (one PC, one camera, 2026-11-25): with one camera connected, the list showed its USB location, and given that location it opened at 1600x800 MJPG and read one frame; a location no device has was refused (Python DirectShow, Rust Media Foundation); not run with two cameras. | none | `--synthetic` (a made-up list of two, generated frames) |
| `threaded_capture.py` | Reads on one thread, processes the latest frame on another (a queue of one); counts the frames skipped | none | `--synthetic` |
| `brightness_stats.py` | Per-eye mean, min, max and share of saturated pixels for N frames, into a CSV | none | `--synthetic` |
| `handle_stall.py` | On `DeviceError` (including one eye stopping): close, ask for the USB cable to be re-inserted, reopen; gives up after N tries | none | `--synthetic` (a fake capture) |
| `calibration_info.py` | The installed calibration: K, D, eye size, R, t and baseline (mm), or the SDK's message when there is none | no camera | `--synthetic` (a made-up calibration in a temporary folder) |
| `calibration_check.py` | Whether a calibration file fits the camera: how far features matched between the eyes lie from the file's epipolar lines (median, 95th percentile) and the share with positive disparity — numbers only, no pass/fail. `--pairs-dir` checks saved PNG pairs instead of the camera | none | `--synthetic` (generated frames, checked against the made-up calibration and a wrong one) |
| `export_recording.py` | Writes the frames of a recording (`record_video.py`, the viewer's `v`) as left/right PNG pairs into a new or empty folder, with `pairs.csv` (the columns of `save_stereo_pairs.py`, holding the times recorded in the recording's CSV), a copy of the recording's JSON as `capture_info.json`, and with `--npz` the frames in `frames.npz` (the format of `capture_dataset_npz.py`); `--start`, `--every`, `--count` pick the frames, and the last line gives the frames exported and the frames in the recording. From an MJPG recording the PNGs hold what it decodes to. Run with generated recordings, and with a camera recording once on Linux, from source before release. On Windows with one camera (one PC, 2-level USB hub, 2026-11-25, 0.0.7): from MJPG and FFV1 camera recordings it wrote 800x800 8-bit left/right images; covering one lens at a time (left and right as seen from behind the camera, looking where it looks) removed the scene from the SDK eye of the same name. Not run with a camera: Linux left/right; a second unit | no camera | `--synthetic` (records 30 generated frames losslessly, then exports them) |

- **`--synthetic`** uses `opticmix_vision.synthetic`: generated frames and simulated controls with made-up
  ranges. It shows that the code runs; its frame rate, ranges and brightness say nothing about the camera.
  `live_preview.py` and `save_stereo_pairs.py` also take `--headless` to run without a window.
- **The compiled extension**: every example that opens the camera needs it — finding the camera by name
  and the camera controls run in it. Install the wheel (a plain source checkout does not have it).
- **Camera controls** (`list_controls.py`, `set_controls_once.py`, `led_level.py`): reading them, with the ranges
  and defaults the camera reports (`list_controls.py`): verified with the published 0.0.7 wheel on one Weevia S1
  unit, Windows 11, one PC, two-level USB hub, two USB re-insertions, read-only. Writing them, and the illuminator
  (`set_controls_once.py`, `led_level.py`): measured with the earlier Python implementation; with the Rust
  implementation (since 0.0.3) they have not yet been verified against the camera. Write once, at startup — see
  *Camera controls* in the [package README](../README.md).
- **Timestamps** (`host_ns`) are the host's monotonic clock right after each frame was read, not a
  timestamp from the camera.
- **Images are as captured**: not rectified, no depth — rectification and depth are not in this package.
- **Platform**: Windows. On Linux (experimental) `measure_fps.py`, `record_video.py`, `play_recording.py`, `save_stereo_pairs.py`, `list_controls.py` and `open_by_usb_location.py` have been run once with one camera (2026-11-25), and `export_recording.py` with a camera recording once, from source before release; the viewer, the explorer and the others have not.
- Of the six examples added in 0.0.4, `play_recording.py`, reading a recording back, seeking and looping: verified with the published 0.0.7 wheel on one Weevia S1 unit, Windows 11, one PC, two-level USB hub, two USB re-insertions, read-only; the `--speed` factor: not verified. `threaded_capture.py`,
  `brightness_stats.py`, `handle_stall.py` and `calibration_info.py` have been run without a camera only;
  `list_devices.py`: its DirectShow list has been run with the camera once (one PC, one camera, 2026-11-25, with the 0.0.6 code): with one camera connected, the list showed its USB location.
- `calibration_check.py` (added in 0.0.5) has been run without a camera only (generated frames and
  generated PNG pairs); not run with the camera.
